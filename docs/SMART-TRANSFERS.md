# Smart floor transfers

## Architecture analysis before implementation

Next.js App Router / React / TypeScript, Zod request validation, SheetJS source parsing and exports, Lucide icons, and global green/gold CSS. `app/page.tsx` hosts the workspace; `components/operations-desk.tsx` hosts register forms and reports. `app/api/workspace/route.ts` handles authenticated operations, contacts and imports. `lib/store.ts` serializes mutations, creates versioned snapshots, and atomically replaces a local JSON file. `prisma/schema.prisma` describes a future PostgreSQL CRM but is not the runtime database. No animation package is needed.

Upload → normalized contact import → separate MMS receipt; source AP/TN/KA/HI/KL pools → language physical row ranges → manual dispatch register → reports/backups. Uploaded contacts are a separate reference scope, not automatically appended to these language sheets. Existing dispatch records are persisted ledger entries, not proof of external file delivery. New smart transfers record an explicit committed status, operator, immutable allocations and downloadable workbook.

Reuse: source mapping and name/phone eligibility, operations register, authentication, audit, backups, serialized mutation queue, styles. Affected: operations desk, new transfer component/domain/API/download route, store types, source mapping, operations save validation, backup export, tests. Existing accounts and records remain intact; no seed replacement or guessed floor identifiers.

Legacy ledger source-row order represents entry order; business dates in this workbook are inconsistent. Manual entries use server creation time. Floor/language continuation follows the last structurally valid persisted dispatch, with incomplete source matches blocking further automation for that sequence. File sequences follow the latest named ledger entry, preserving its prefix, numeric width and extension. Known legacy overlaps remain visible and consume their referenced rows globally. Repeated deliveries were previously possible; new transfers reject overlaps across all floors in the shared source pool.

Risks: malformed ranges, missing source rows, unsupported naming patterns, historical numbering anomalies, changing source workbook, and unconnected PostgreSQL/authentication. A new floor/language requires an explicit starting row when no previous sequence exists; the server validates it without silently skipping rows. No arbitrary 1,000-lead default or floor-derived prefix is introduced.

## Planned compatible implementation

Calculate previews on the server, return counts/ranges only, increment recognized filenames, and require explicit initial filenames for new sequences. Unknown legacy formats require an explicit numeric template. Revalidate preview fingerprints inside the existing serialized mutation, save allocations/export/audit/dispatch together, reject duplicate names and rows, and persist idempotency receipts. Failed mutations do not advance sequences. Use a guided responsive configuration/preview dialog and existing register history.

Production must replace the local adapter with database transactions, globally unique filename/allocation constraints, distributed locking and authenticated identities. Local guarantees apply only to one Node process; do not run multiple workers against this JSON file.

## Implemented API and storage

`POST /api/transfers` accepts `preview` or `commit` with floor, per-language quantities, optional initial starting rows and initial filename. The server parses occupied name/phone rows and computes a source workbook hash. The preview includes availability, previous ranges/file, candidate ranges/file, problems and a fingerprint. Commit recalculates under `mutate`, rejects changed fingerprints, creates a dispatch, immutable source row allocations, an Excel artifact, an operator audit entry, and a persisted idempotency receipt. The final serialized store is backed up and then atomically renamed. A backup failure prevents saving. Only a successful store replacement advances the next sequence. Retry checks occur before reading the source, allowing recovery even if the source is later unavailable.

The allocation identity is language + physical source row in the fixed AP/TN/KA/HI/KL workbook. All known historical dispatch ranges reserve those identities across floors, including partially counted legacy ranges. An unparseable historical range blocks that language until corrected. This is conservative row allocation, not global phone deduplication. A language's last ledger entry with a range establishes continuation; an incomplete previous range cannot advance. When no prior language range exists, the first eligible source row is displayed, and an explicit starting row can be provided. Gaps/headers/missing/occupied rows inside a candidate range block it; quantity is never truncated or silently filled from disjoint rows.

Filenames preserve the most recent named ledger entry's prefix, zero padding, suffix and extension. A calendar date alone is not interpreted as an incrementing number. Numeric regressions in a legacy pattern require a new explicit starting filename above every used number, or a new prefix. Downloads use `.xlsx`; unsupported extensions/names need a reviewed `.xlsx` sequence. The initial committed filename becomes the rule for subsequent deliveries. Names are case-insensitively unique across the whole register and transfer receipts. No existing artifact is overwritten.

`GET /api/transfers` supplies paginated immutable history (25 per page), with floor/search filtering, and omits artifacts and retry secrets. `GET /api/transfers/[id]/file` downloads the stored immutable workbook (language sheets with name, phone, source sheet and source row, plus transfer metadata). It does not regenerate the file from potentially changed Google data. Existing daily register/dashboard/CSV and Excel backups reflect the same committed dispatch. Backup workbooks include TRANSFER HISTORY; the JSON backup includes full allocation and export restore data.

New deliveries must use smart confirmation; the old operations-save endpoint cannot create a dispatch or edit a smart transfer. Legacy correction remains available for resolving errors, but cannot overlap immutable smart allocations. Source refresh does not edit smart transfers. Refresh matches legacy records by physical source register row, so source reordering still needs manual reconciliation.

## Interface and recovery

Send to floor opens a responsive two-panel dialog: floor/languages/quantities on the left, calculated filename, previous/next ranges, availability, total and blocking explanations on the right. No guessed quantity default is introduced: previous language quantities are reused where known; new sequences ask for quantities. Rows are calculated on the server rather than downloading source contacts to the browser. A success view provides the immutable workbook download; register rows also link it. Search includes operator notes; expanded records contain operator, timestamp and transfer ID.

The dialog traps keyboard focus, supports Escape, restores prior focus, locks background scrolling, disables double submissions, uses loading indicators, and follows existing green/gold styles and reduced-motion rules. A tab-session draft stores only configuration and pending retry key/token, not lead contact data. Reload and reopen Send to floor to recover an interrupted confirmation; retrying the same key returns the same committed record. Network uncertainty locks changes until confirmation recovery. Closing an unconfirmed preview consumes nothing. Rejected authenticated commits record a failed audit event with floor, quantities, retry key and reason when storage is available; no failed allocation or file number is consumed. If storage/backup itself is unavailable, rejection auditing is best effort and the original failure is returned. An unconfirmed preview is not a reservation or a transfer, so closing it does not create a cancellation record. Only committed records are counted.

## Permissions and deployment limits

Operations remain available to Admin and the existing designated operator `u1`. Other Managers, Team Leaders and Employees retain their existing CRM branch/team permissions and cannot access these floor transfers: there is no established floor-to-branch membership model to safely grant them floor access. No new role permission is implied. Immutable transfers have no deletion, archival or reversal endpoint. Existing legacy corrections are audited and active receipts keep filenames/row reservations from being reused.

The database schema is deliberately unchanged because it is not connected to runtime storage. Before deploying across workers/servers: implement PostgreSQL transfer and allocation tables with unique normalized filenames, unique source/language/row allocation keys, idempotency constraints, serializable transactions or locks and indexed floor/history queries; migrate and reconcile the legacy ledger; configure real authentication and floor memberships. Use a durable source identity and migration process before reordering or replacing language pools. Add off-machine encrypted backups and retention, artifact/object storage, monitoring and paginated workspace reads. This local adapter retains entire JSON state and exports in snapshots and therefore suits the current small local workspace, not an unlimited database.

Google write-back remains unconfigured; the app records local transfers/backups. A committed record means a local allocation was saved, not that the destination operator downloaded or received it. Failed backup snapshots cannot consume sequences, although a successful pre-save snapshot followed by a failed primary save may contain an uncommitted candidate; restore decisions must use the primary committed state or reconcile manifests.

## Validation

Final verification on 12 October 2026: all 36 unit/domain/store tests passed; production build and TypeScript checks passed; isolated production API integration passed. Existing business data remained at 55 operations (48,716 received / 34,552 dispatched matched rows), with no test transfers added to it. Desktop/mobile preview, draft recovery and keyboard checks are detailed below.

`npm test` exercises the existing import/permissions/backup workflows plus transfer filename patterns, first/next/multi-language allocations, independent floor sequences, cross-floor conflicts, gaps, insufficient stock, source changes, idempotent replay, permissions, legacy ordering/invalid ranges/numeric regressions, concurrency and backup rollback. `npm run test:transfers:api` creates a temporary workspace/source and starts the built app on port 3101, testing the production API without touching business data. It covers authorization, preview, concurrent retries/conflicts, export content, history/dashboard integration, immutable edits and old save-path bypass blocking. Run `npm run build` before the integration test. There is no lint script configured.

Browser checks: 1280px desktop and 390px mobile configuration/preview layout, no horizontal page overflow on mobile, live quantity recalculation (Tamil 100 → 101 updates end 12100 → 12101), read-only calculated filename, historical overlap/unresolved blockers, Escape restoring focus to Send to floor, and configuration recovery after reload/reopening. Browser error/warning logs were empty during the checked preview. No business transfer was confirmed during UI testing. A 50,000-source-row unit fixture produced bounded preview metadata without customer data (11ms measured in the test run; not a production benchmark).
